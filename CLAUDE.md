# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Run

```bash
./build.sh debug                 # Android debug APK
./build.sh release               # Android release APK (requires signing env vars)
./build.sh desktop               # Linux AppImage (requires appimagetool in PATH or $APPIMAGETOOL)
./gradlew :desktopApp:run        # Run the desktop app
./gradlew :shared:desktopTest :desktopApp:test   # Tests
./install-all.sh [--build]       # Install debug APK on all connected devices
```

Release signing requires env vars: `KEYSTORE_FILE` (default `~/.android/release-key.jks`), `KEYSTORE_PASSWORD`, `KEY_ALIAS` (default `release`), `KEY_PASSWORD` (defaults to `KEYSTORE_PASSWORD` when unset).

Tests live in `shared/src/jvmSharedTest` (ODS export, date helpers, web app), `shared/src/desktopTest`
(scheduler desktop, migrazione 2→3, scrittura condizionata), `desktopApp/src/test` (autostart, single
instance, porte) e `shared/src/androidInstrumentedTest` (riprogrammazione al boot, TLS di piattaforma,
lettura del corpo HTTP — richiede un dispositivo o l'emulatore).

## Prova della UI desktop in una sessione X separata

```bash
tools/sessione-x.sh avvia [--dati-reali]   # Xephyr + metacity + AppImage su :2
tools/sessione-x.sh browser URL            # un browser sull'URL, nel display separato
tools/sessione-x.sh pilota                 # comandi di Pilota.java da stdin
tools/sessione-x.sh scatto [file]          # screenshot del display separato
tools/sessione-x.sh chiudi
```

`browser` serve a guardare la web app locale (`web/`) servita dal telefono: profilo nuovo sotto
`build/`, così il browser dell'utente non si trova una sessione in più aperta. Con l'emulatore,
l'indirizzo da passare è quello di `adb forward tcp:9888 tcp:9888`, cioè `127.0.0.1`.

Serve a guidare l'app senza rubare mouse, fuoco e appunti alla sessione dell'utente. `Xephyr` è
un server X vero — display, albero di finestre e puntatore propri — ma annidato in una finestra
di `:0`, così la prova si guarda mentre succede; per l'accesso remoto ci si mette sopra
`x11vnc -display :2`. `Xvfb` sarebbe headless e non mostrerebbe niente.

Il pilotaggio è `java.awt.Robot` avviato con `DISPLAY=:2` (`tools/Pilota.java`): XTEST consegna
gli eventi al server X del client che li inietta, quindi su `:0` non arriva nulla — verificato
campionando puntatore, `_NET_ACTIVE_WINDOW` e appunti durante una raffica di comandi. L'unico
momento in cui `:0` cambia fuoco è `avvia`, perché ci si apre una finestra nuova.

Quattro cose da sapere prima di fidarsi della prova:

- **Un'istanza per macchina.** `SingleInstance` tiene la porta di loopback 47653, che non è legata
  al display: con un'altra copia viva quella nella sessione separata si chiude appena parte.
- **La sandbox isola i file, non la rete.** `XDG_DATA_HOME`/`XDG_CONFIG_HOME` spostano database,
  `device-id`, voce `.desktop` e icona in `desktopApp/build/sessione-x/sandbox`, ma l'istanza
  resta un peer a tutti gli effetti: se la si associa a un dispositivo vero, la sincronizzazione
  porta dentro i promemoria reali e vi lascia un peer che smette di rispondere quando la si
  smonta. Per una prova di sincronizzazione va bene; per una prova isolata, non associarla.
- **Le notifiche escono comunque.** `notify-send` passa dal DBus di sessione, non da X: un allarme
  che scatta durante la prova compare sul desktop reale.
- **Niente tray e niente GL.** In Xephyr `isTraySupported` è falso (l'app lo gestisce da sé) e
  Skiko ripiega sul rendering software: `Cannot create Linux GL context` nel log è atteso.

Le coordinate dei click si ricavano dagli screenshot: non c'è un albero di accessibilità da
interrogare, quindi ogni azione va guardata prima e verificata dopo — meglio ancora
controllando il database della sandbox, che dice quale riga è stata toccata davvero.

## Architecture

Compose Multiplatform project targeting Android and desktop JVM, MVVM throughout.
Package: `it.agoldoni.reminder`.

**Modules:** `:shared` (dominio, dati, ViewModel, schermate), `:androidApp` (Application,
MainActivity, manifest, risorse), `:desktopApp` (main, tray, autostart, packaging).

**Source set di `:shared`:** `commonMain` (Kotlin puro), `jvmSharedMain` (condiviso dai due
target JVM, dove `java.*` è disponibile — `OdsExporter` e le date stanno qui), `androidMain`,
`desktopMain`. Il gruppo `jvmShared` è dichiarato con `applyDefaultHierarchyTemplate`; il
`dependsOn` manuale non è ammesso.

**Layers:**
- **`data/`** — Room KMP (`reminder.db`), single entity `EventEntity` with DAO. Schema is at version 5 (`events` + `peers`); migrations live in `AppDatabase.Companion` and use `SQLiteConnection`, not `SupportSQLiteDatabase`. `MIGRATION_1_2`, `MIGRATION_3_4` e `MIGRATION_4_5` sono `object`, mentre la 2→3 è la funzione `migration2to3(deviceId)`: serve l'identità del dispositivo per popolare `origin` delle righe preesistenti. `AppDatabase` needs `@ConstructedBy` plus the `expect object AppDatabaseConstructor`. Driver: `AndroidSQLiteDriver` su Android, `BundledSQLiteDriver` su desktop (dove `sqlite-bundled` è dichiarato solo in `desktopMain`, per non appesantire l'APK). Schema esportato in `shared/schemas/`.
  Dalla v3 l'entità porta i campi della sincronizzazione: `uuid` (identità globale, indice unico), `updatedAt`, `deleted`/`deletedAt` (tombstone) e `origin` (dispositivo di nascita, immutabile). `id` resta la chiave primaria perché è il requestCode dei `PendingIntent`. **La cancellazione è logica**: le letture dell'app filtrano `deleted = 0`, `changedSince()` e `getByUuid()` vedono anche i tombstone. Ogni mutazione riceve l'istante da scrivere in `updatedAt` come parametro (`softDelete(id, nowMillis)`, `markCompleted(id, nowMillis)`, …): il clock è del chiamante, così i test lavorano a tempo virtuale. Chi modifica un evento deve partire dalla riga esistente e usare `copy()`, mai ricostruire l'entità da zero: rigenererebbe `uuid` e perderebbe l'identità vista dagli altri dispositivi.
- **`sync/` (integrazione)** — `SyncController` è un'**interfaccia in `commonMain`** perché `AppContainer` e le schermate vivono lì mentre socket e crittografia stanno in `jvmSharedMain`: stessa ragione per cui `AlarmScheduler` è un'interfaccia. `SyncService` la implementa e tiene insieme ricerca, ascolto, associazione e giri di replica. Il parametro `listensInBackground` distingue i due lati **a schermata chiusa**: il desktop ascolta sempre, Android no — le policy non lasciano tenere un socket aperto ad app chiusa — e il telefono sincronizza chiamando lui da `MainActivity.onStart()`. **Mentre la schermata di sincronizzazione è aperta ascoltano entrambi**: l'app è in primo piano per definizione e un socket in ascolto è lecito. Serve sulle reti dove è il telefono a non raggiungere il PC (sottoreti diverse, NAT asimmetrico): si parte dal lato che passa. Le chiamate di rete sono **bloccanti** e chi le invoca arriva da `viewModelScope`, cioè da `Dispatchers.Main`: `syncNow` e `pair` girano su `withContext(Dispatchers.IO)`, altrimenti Android chiude l'app per ANR. Ci si annuncia **solo se si è davvero in ascolto, e con la porta effettiva**: annunciarne un'altra manderebbe il peer contro un muro. Porta fissa `SYNC_PORT` = `47700` (in `Discovery.kt`), così il fallback manuale è indovinabile; **non può coincidere con `SingleInstance.DEFAULT_PORT` = `47653`** del modulo desktop, che l'istanza singola tiene per tutta la vita del processo — quando coincisero, il server di sincronizzazione non riusciva a legarsi e l'app sembrava funzionare mentre la sincronizzazione era muta. Il presidio è `PorteTest` in `:desktopApp`, l'unico modulo che vede entrambe le costanti. Il flag `sync_enabled` (`AppSettings`) è **spento di default**: finché lo è, `start()` non apre socket e non annuncia nulla; si accende quando l'utente completa la prima associazione. I guasti di rete non risalgono come eccezioni ma diventano `SyncOutcome.Failed` con un messaggio in italiano.
  In `peers` convivono **due tempi diversi** e confonderli è un errore facile: `watermark` (colonna `lastSyncAt`, tenuta com'era perché SQLite sa fare `RENAME COLUMN` solo dalla 3.25 mentre l'API 26 si ferma alla 3.18) è l'istante fin dove si è replicato **nell'orologio del peer**, e non va mai mostrato; `lastContactAt` è l'ora **locale** dell'ultima sincronizzazione riuscita, ed è quella che va in interfaccia. Anche `SyncStatus.lastSyncAt` si ricava dai peer e non dalla sessione, altrimenti la schermata direbbe «mai sincronizzato» dopo ogni riavvio.
- **`di/`** — `AppContainer`, container scritto a mano (niente Hilt: non funziona in KMP). Le implementazioni di piattaforma vengono costruite dal modulo applicativo e passate al container; le schermate lo raggiungono via `LocalAppContainer`.
- **`platform/`** — `expect`/interfacce per ciò che cambia fra piattaforme: `AlarmScheduler`, date, colori dinamici, `AppInfo`, `ExportTarget`, `newUuid()`. `localDeviceId()`/`localDeviceName()` vivono nei rispettivi `platform/` di Android e desktop: identità stabile e nome leggibile del dispositivo.
- **`ui/`** — Compose screens with per-screen ViewModels injected via `AppContainer.viewModelFactory`. Navigation via `NavHost` with string routes: `list`, `edit/{eventId}` (0 = new), `completed`, `sync`.
  La schermata `sync` **mostra un codice da confrontare, non un campo in cui digitarlo**: è la conseguenza diretta della scelta crittografica di `Pairing`, e cambiarla in un campo di input renderebbe l'associazione forzabile. Aprirla accende ricerca e ascolto **anche a interruttore spento** (`beginInteractive`), perché altrimenti non ci sarebbe modo di trovare il primo dispositivo da associare; chiuderla li rispegne se nessuna associazione è stata completata. Finché è aperta è anche l'unico posto in cui si può mostrare il codice di un'associazione **in arrivo**: fuori da qui quelle associazioni vengono negate.
- **`alarm/`** — `AlarmScheduler` sets exact alarms via `AlarmManager`. `AlarmReceiver` triggers notifications through `NotificationHelper`. `NotificationActionReceiver` handles snooze (+5min, +1h) and dismiss actions from notifications. `BootReceiver` reschedules all future alarms on device restart.
- **`sync/`** — scoperta dei dispositivi, associazione, canale cifrato e replica. **Sulla replica ci sono due scelte che sembrano dettagli e non lo sono.** (1) `changedSince` include l'estremo (`>=`, non `>`): il watermark è l'`updatedAt` più recente già ricevuto e nello stesso millisecondo può essercene un altro scritto dopo lo scambio precedente — escluderlo lo perderebbe per sempre, mentre rispedirlo costa un evento che il merge scarta da sé. (2) Nella conversazione i due lati si scambiano **prima le domande e poi le risposte**: chi rispondesse dopo aver applicato il lotto dell'altro gli rimanderebbe indietro i suoi stessi eventi, e il watermark rifletterebbe l'orologio sbagliato. Per lo stesso motivo il watermark è `Push.upTo` — l'istante dichiarato dal mittente — e non il massimo `updatedAt` del lotto, che può contenere eventi nati altrove. `resolveMerge` è una funzione pura, separata dall'applicazione, e a parità di `updatedAt` decide con una firma testuale del contenuto: serve un criterio che dia lo **stesso** vincitore su entrambi i dispositivi, e «vince il remoto» darebbe risultati opposti sui due lati. Un tombstone non è un caso a parte, è un evento con `deleted = true` — è per questo che una cancellazione non risorge. L'idempotenza non viene da un controllo sui duplicati ma dal fatto che il confronto è per `uuid` e la regola scarta ciò che non è più recente.
  Associazione e canale cifrato: le parti crittografiche stanno in `jvmSharedMain` (`javax.crypto` c'è su entrambi i target: niente `expect`/`actual`). Curva **P-256** e non X25519, che su Android arriva solo con l'API 31 mentre il minimo qui è 26. HKDF-SHA256 è scritto a mano (non c'è in JCA) e verificato contro i vettori della RFC 5869. L'associazione usa il **confronto a vista**: entrambi i lati derivano dallo scambio lo stesso codice a sei cifre e l'utente conferma di vederlo uguale sui due schermi — un codice digitato da un lato solo sarebbe forzabile offline da chi si mette in mezzo. `SecureChannel` è AES-256-GCM con **una chiave per direzione** (due contatori sulla stessa chiave produrrebbero nonce ripetuti, che in GCM azzerano ogni garanzia) e il numero di sequenza come dato autenticato, così un frame ripetuto o spostato non si decifra. Il `sharedSecret` sta in chiaro nella tabella `peers`: è protetto dai permessi del file, non da una cifratura a riposo.
  Scoperta dei dispositivi sulla rete locale: il contratto (`Discovery`, `DiscoveredPeer`, `DiscoveryStatus`, `Advertisement`) sta in `commonMain` con il tipo di servizio `_promemoria-sync._tcp`; l'attributo TXT `deviceId` porta l'identità. `NsdDiscovery` (Android) tiene un **multicast lock** — senza `CHANGE_WIFI_MULTICAST_STATE` il Wi-Fi scarta gli annunci — e serializza le `resolveService`, che `NsdManager` accetta una alla volta. `JmdnsDiscovery` (desktop) passa a jmdns un indirizzo esplicito da `siteAddress()`: `InetAddress.getLocalHost()` su Linux risolve spesso in `127.0.1.1` e l'annuncio non uscirebbe. Il tipo di servizio va scritto `_promemoria-sync._tcp` per `NsdManager` e `_promemoria-sync._tcp.local.` per jmdns. `PeerDirectory` (commonMain) unisce i peer trovati a quelli inseriti a mano quando mDNS non passa: è una sorgente in più della stessa lista, non una modalità separata.
- **`export/`** — Reminder export to ODS file. `Exporter` restituisce un `ByteArray` (il contratto vive in `commonMain`); la consegna passa da `ExportTarget`: share intent su Android, dialog di salvataggio nativo su desktop. `OdsExporter` writes a minimal ODF 1.2 spreadsheet (ZIP with `mimetype` STORED + `META-INF/manifest.xml` + `content.xml`) by hand — no third-party ODS library, since SODS pulls in `javax.xml.stream` (StAX) which is unavailable on Android. `ExportEventsUseCase` reads events from DAO based on `ExportFilter` (`ALL` / `OPEN_ONLY`), writes the file in `cacheDir/exports/`, and returns a `content://` Uri exposed via `FileProvider` (authority `${applicationId}.fileprovider`, paths in `res/xml/file_paths.xml`). `ShareHelper` builds the `ACTION_SEND` chooser. The `Exporter` interface allows future formats (CSV/XLSX) without rewriting callers.
- **`web/`** — porta HTTPS attivabile che espone ai browser della rete locale la vista principale. Dalla feature 004 **si può anche scrivere**: modificare, creare, completare. Non cancellare — è l'unica operazione che dal browser non si potrebbe disfare, e resta un lavoro da app. Solo Android la cabla; il codice sta in `jvmSharedMain` (è `java.net` puro) con l'interfaccia `WebServerController` in `commonMain`, per la stessa ragione di `SyncController`. `AppContainer.web` ha un default **inerte** (`WebServerNonDisponibile`) così il desktop non deve conoscerla.
  **Porta `WEB_PORT` = 9888.** È la terza porta fissa dell'app e non può coincidere con `SYNC_PORT` (47700) né con `SingleInstance.DEFAULT_PORT` (47653): sul telefono i due server possono ascoltare insieme. `PorteWebTest` e `PorteTest` sono il presidio.
  **Vive quanto il processo, non quanto una schermata.** `WebService` è costruito in `ReminderApp.onCreate()`. Legarlo all'Activity vorrebbe dire chiudere e riaprire il socket a ogni **rotazione dello schermo** — che è un giro completo di `onStop`/`onStart` — lasciando la pagina senza risposta ogni volta che qualcuno gira il telefono in mano. Fino alla 005 la ragione era peggiore: una rotazione **rigenerava il token** e l'indirizzo appena digitato smetteva di funzionare. Dalla 006 non più.
  **La porta resta aperta ad app chiusa**, tenuta viva da `WebServerService`, un servizio in primo piano. Non è ridondanza: un socket aperto in un processo in background è inutile, perché il processo viene congelato o ucciso e Doze taglia la rete. Quattro cose da sapere: (1) il tipo dichiarato è **`specialUse`** e non `dataSync`, perché da Android 15 quest'ultimo ha un tetto di sei ore al giorno — una porta che si chiuderebbe da sola a metà giornata; (2) `START_NOT_STICKY`, e **dalla 006 per una ragione diversa**: quella vecchia — a processo ucciso il token ricomincerebbe diverso — non vale più, perché i token sopravvivono al processo; vale però che a servizio riavviato dal sistema **nessuno aprirebbe il socket**, visto che la porta la apre `resume()` da `MainActivity.onStart()` e lì non c'è nessuna Activity: tornerebbe la notifica, non il servizio che dichiara. `START_STICKY` è ora possibile e desiderabile, ma vuole che sia il servizio ad aprire la porta; (3) dall'API 31 il sistema **rifiuta** `startForegroundService` da un'app che non è davanti, ed è per questo che `resume()` si chiama da `MainActivity.onStart()` e non da `ReminderApp.onCreate()` — un rifiuto non chiude la porta ma diventa un messaggio, perché finché l'app è aperta funziona lo stesso; (4) l'azione «Spegni» della notifica chiama `disable()` e quindi spegne **l'interruttore**, non solo il servizio: fermare il servizio lasciando acceso il flag farebbe riaprire la porta alla successiva apertura dell'app. La notifica non porta l'indirizzo: il token finirebbe sulla schermata di blocco.
  **Gli asset stanno in `shared/src/webAssets/`**, dichiarata a mano a **entrambi** i target in `shared/build.gradle.kts`. Le `resources/` di `jvmSharedMain` non vengono raccolte da AGP — verificato con `:shared:sourceSets` — quindi finirebbero nel jar desktop ma non nell'APK, e il guasto sarebbe una pagina bianca a runtime. Si leggono dal classloader, che sull'APK funziona.
  **L'indirizzo è fisso e la credenziale è un JWT** (feature 006). L'indirizzo è `https://IP:9888/` e basta; il permesso è un JWT HS256 (`Jwt.kt`) che il telefono consegna **una volta sola** nel frammento (`#access=…`) e che il browser tiene in `localStorage` e presenta come `Authorization: Bearer`. Il frammento **non viene mai spedito al server**: il segreto sparisce da log, cronologia e barra dell'indirizzo. Fino alla 005 erano 8 caratteri nella query rigenerati a ogni accensione, e da lì venivano tre difetti che si tenevano per mano: il segnalibro si rompeva a ogni riavvio del processo, il codice era in bella vista, e non c'era modo di togliere un accesso già dato.
  **La regola che rende sicuro un verificatore JWT scritto a mano è una sola, e va scritta nel sorgente: firma prima, payload poi, header mai.** Si ricalcola l'HMAC sui **byte grezzi** dei primi due segmenti e si confronta con `constantTimeEquals`; solo dopo si legge il payload. `seg0` non si decodifica in nessun punto — nemmeno per confrontarlo con il nostro, perché la firma già lo copre — quindi `alg: none` e la confusione fra algoritmi **non hanno un posto dove entrare**. Stessa forma di difesa di `StaticAssets`, dove la risalita non è filtrata ma resa impossibile. Nessuna eccezione esce da `Jwt`: `Base64.getUrlDecoder()` e `decodeFromString` lanciano volentieri, e un'eccezione qui sarebbe un `500` invece di un `401`.
  **`iat` ed `exp` sono in secondi** (RFC 7519) mentre il resto dell'app è in millisecondi: la conversione avviene **dentro `Jwt` e in nessun altro posto**. Un'unità mista lasciata girare produce un token che scade fra cinquant'anni o fra mezz'ora, e non si nota finché non è tardi.
  **La chiave di firma sta in `filesDir/web-tls/firma.key`**, accanto a quella TLS e protetta dalla stessa cosa: i permessi del file (`soloPerNoi`), non una cifratura a riposo. `ChiaveFirma` ricalca `CertificateStore` **avvertenza compresa** — guardia in un punto solo, cache in memoria — perché `apri()` è chiamata anche da `resume()`, cioè a ogni rotazione dello schermo, e una chiave rigenerata lì butterebbe fuori ogni browser senza che nessuno abbia toccato niente. Le porte da cui una chiave nuova può entrare sono **due sole**: la prima accensione e `revoca()`. Un file di lunghezza diversa da 32 byte **non si rigenera sul posto**: si cancella, la porta non si apre e la ricrea il riavvio dell'app — perché ricrearla è una revoca di massa e una revoca di massa non deve essere silenziosa. Cancellare è ciò che impedisce a `resume()` di ripetere lo stesso rifiuto per sempre.
  **Spegnere l'interruttore non revoca più niente**: chiude la porta, non cambia le serrature. La revoca è un gesto suo (`WebServerController.revoke()`), globale, ed è la rotazione della chiave: non c'è nessuna lista di token emessi da cui togliere una riga. È disponibile anche a interruttore spento, perché chi spegne credendo di revocare deve trovare lì il gesto vero. Il token dura **30 giorni secchi**: niente rinnovo a scorrimento, che trasformerebbe «30 giorni» in «30 giorni di inattività».
  **`/` è pubblica**, e non è una rinuncia: il browser non può mandare un header prima di aver caricato il JavaScript, quindi la pagina dev'essere il **guscio** che poi si autentica. `index.html` non contiene promemoria; il prezzo — una richiesta senza credenziali rivela che il servizio è acceso — era già stato accettato dalla 002 per `/app.css`. `Asset.tokenRichiesto` resta anche se oggi vale `false` su tutte e sei le righe: non è il controllo, è ciò che obbliga la settima risorsa a nascere con una decisione presa.
  **`401` e `403` sono due cose diverse e il client le usa.** `401` = «non so chi sei»: assente, malformato, firma sbagliata, scaduto **o** bloccato dalla soglia — le quattro restano indistinguibili sul filo, per la ragione della 002. `403` = «so chi sei e questo indirizzo permette solo di guardare», e lo vede solo chi ha già un token valido. La distinzione serve al browser per decidere **se buttare via il token**: su `401` sì, su `403` mai — quel token è buono. Niente `WWW-Authenticate`: non serve a un client nostro e allarga la superficie.
  **La soglia di 10 tentativi al minuto per indirizzo IP resta**, ma difende un'altra cosa: contro una firma da 256 bit non serve più a fermare chi indovina, serve a bocciare chi sonda a raffica. Il contatore è **uno solo** anche con due token — è per IP, non per token: sdoppiarlo regalerebbe venti tentativi al minuto invece di dieci. Un token valido ma **insufficiente** non consuma tentativi: chi apre l'indirizzo di lettura e tocca un pulsante è l'utente, non un attaccante. Un guasto della chiave dà `NEGATO` senza consumare tentativi: non è colpa di chi chiede.
  **`Referrer-Policy: no-referrer` resta**, anche se ora il token non è più nell'URL: costa una riga e la ragione per cui c'era potrebbe tornare.
  **I token sono due**, non uno con due livelli: uno apre la pagina in sola lettura, l'altro permette anche di modificare, e differiscono nel solo campo `p` del payload. Il potere sta **in quale dei due si è consegnato**, non in un interruttore dell'app, e la conseguenza è che quello di lettura si può dare a qualcun altro. Si coniano insieme, dallo stesso istante, quindi la scadenza mostrata è **una sola**. Coniarne di nuovi — cosa che `apri()` fa a ogni apertura della porta, quindi anche a ogni `resume()` — **non invalida quelli consegnati prima**: l'indirizzo sullo schermo è un buono di consegna fresco, non l'identità del servizio, ed è esattamente questo a distinguerlo da `ChiaveFirma`, dove la stessa disinvoltura sarebbe il difetto peggiore della feature.
  **`localStorage` è per origine, quindi un browser conserva un token solo:** aprire l'indirizzo di sola lettura su un browser che aveva quello completo lo **declassa**, e viceversa. È prevedibile e reversibile, ma va saputo. E «fisso» è vero finché è fisso l'indirizzo IP: cambiata rete, cambia l'origine e serve una riconsegna — il token però non è legato all'indirizzo, quindi basta quella.
  **Un permesso che arriva a pagina già aperta va raccolto con `hashchange`, e non è un caso limite.** Incollare `…/#access=…` in una scheda che sta già su `…/` è una navigazione **nello stesso documento**: il browser non ricarica e lo script non riparte. Senza quell'ascoltatore la pagina resta con il permesso di prima — o senza nessuno — mentre la barra mostra quello nuovo, e il difetto **non si vede**: l'utente ha fatto la cosa giusta e non succede niente. Succede tutte le volte che si consegna un indirizzo dopo una revoca o si passa dalla lettura alla scrittura. Adottando il token nuovo si azzera anche l'`ETag` (i permessi stanno dentro il corpo, quindi l'impronta cambia) e si **interrompe** la richiesta in corso: se il permesso di prima era stato revocato risponderebbe `401`, e la pagina cancellerebbe il permesso appena arrivato.
  Nella schermata dell'app l'indirizzo di sola lettura è **quello visibile** e quello completo sta dietro un tocco. Non è per frequenza d'uso — si copiano entrambi di rado — ma perché i due differiscono solo negli otto caratteri finali, quindi affiancati sono indistinguibili, e i due errori non pesano uguale: copiare quello completo credendo di copiare l'altro regala il telecomando **senza dare nessun segnale**, mentre l'errore opposto si scopre in tre secondi.
  **Si scrive tutte le volte che la porta è aperta, anche ad app chiusa.** Una prima stesura lo permetteva solo con l'app in primo piano, per prudenza e perché non si sapeva se scrivere ad app chiusa funzionasse; la verifica sul dispositivo dice che funziona — database **e** sveglie, con `MainActivity` distrutta e il processo tenuto vivo dal solo `WebServerService`. Restare stretti avrebbe voluto dire rifiutare qualcosa che funziona, cioè rispondere una bugia, e come difesa quel cancello non fermava chi ha il token e sceglie il momento. Di conseguenza `MainActivity` **non ha un `onStop`**, il payload non porta nessuna disponibilità e la pagina non ha uno stato spento.
  **Ogni scrittura risponde con la lista intera e il suo `ETag`**, cioè con l'uscita di `corpoEventi`: una sola funzione costruisce la rappresentazione, quindi lettura e scrittura non possono divergere, chi ha salvato non fa un giro di rete in più, e la richiesta condizionale successiva riceve `304` da sé. Vale anche per il `409`, che porta il valore vero a chi ha perso il confronto. Ciò che è stato scritto viaggia invece in un **header** (`X-Promemoria-Scritto`): nel corpo cambierebbe l'impronta, e senza di esso non si potrebbe annullare una completazione — l'evento completato esce dalla lista degli aperti e il suo `updatedAt` nuovo non è più da nessuna parte.
  **Il controllo dei conflitti è un `UPDATE … WHERE updatedAt = :atteso`** (`EventDao.updateIfUnchanged`), non un leggi-confronta-scrivi: ogni connessione è servita da una coroutine sua, quindi due richieste potrebbero superare entrambe il confronto. Nella `SET` non ci sono `uuid` e `origin`, e non è una dimenticanza: non potendoli nominare non si possono perdere.
  **`advanceMinutes` accetta solo {0, 5, 15, 30, 60}.** Non è simmetria con l'app: `EventEditScreen` sceglie l'etichetta con `first { … }` senza `orNull`, quindi un valore fuori elenco scritto dal web farebbe **lanciare l'editor dell'app**, e il promemoria non sarebbe più modificabile dal telefono.
  **Il corpo delle richieste si legge, ma solo su un `Content-Length` dichiarato, numerico, singolo e sotto `MAX_CORPO`.** Tutto ciò che rende la lunghezza ambigua — `Transfer-Encoding`, due `Content-Length`, un numero con dentro una virgola — si rifiuta invece di interpretarlo; il `Content-Length` ripetuto va colto **prima** che la mappa degli header lo fonda in un valore solo. Si legge con un ciclo scritto a mano e **non con `readNBytes`**: quel metodo c'è sulla JVM da Java 9 ma non su Android al `minSdk` 26, e il guasto non è rumoroso — muore dentro la coroutine, il socket si chiude muto, e `curl` dice `000` invece di un codice. Presidio: `CorpoPiattaformaTest` in `androidInstrumentedTest`, come per il `KeyStore` della 003.
  **Le scritture pretendono `Content-Type: application/json`** e rispondono `415` altrimenti: un modulo HTML cross-origin può inviare solo tre tipi, nessuno dei quali questo, quindi il preflight CORS lo ferma. Costa una riga ed è la difesa dal CSRF che sta *sopra* quella vera, che è il token.
  **`ScrittureWeb` è l'unico punto che tocca database e allarmi insieme**, e riusa la regola di `SyncEngine.reschedule` (`cancel` e poi `schedule` se non completato). Un secondo posto da cui scrivere sarebbe un secondo posto in cui dimenticarsi la sveglia, e quel difetto non si vede: il dato è giusto e la notifica arriva all'ora vecchia.
  **Gli asset si servono da un elenco chiuso** (`StaticAssets.AMMESSI`): un percorso che non è una chiave di quella mappa non esiste, quindi la risalita non è respinta ma impossibile. Il controllo sui `..` nel parser è una seconda rete, e la decodifica percentuale avviene **una volta sola** (due volte farebbero passare `%252e%252e%2f`).
  **Un difetto del gestore va catturato dentro `client.use`**, non fuori: lasciandolo uscire, il socket è già chiuso e il `500` non parte più. È già successo, e il test lo presidia.
  **L'aggiornamento è condizionale**: `/api/eventi` porta un `ETag` e a `If-None-Match` uguale risponde `304`, così la pagina non si ridisegna e non perde la posizione di scorrimento. L'impronta si calcola sul **corpo**, non su `max(updatedAt)`: completare un promemoria lo toglie dagli aperti e quel massimo può *scendere*. `Cache-Control: no-store` non è in contraddizione — l'impronta la tiene il JavaScript in una variabile, non la cache HTTP.
  **Dalla feature 005 la pagina non interroga più a intervalli: aspetta.** Con `?attendi=1` la richiesta resta appesa finché l'impronta non cambia o finché non scadono `ATTESA_MILLIS` = 25 s, e allora è `304`. È entrata senza toccare il trasporto perché il modello c'era già: `gestisci` è `suspend` e ogni connessione ha la sua coroutine, quindi un'attesa non aggiunge una macchina, aggiunge una sospensione — mentre SSE avrebbe preteso una risposta scritta a rate, cioè riaprire la questione dello stato di connessione che la 002 aveva chiuso. **Il parametro è un interruttore e non una durata**: quanto si aspetta lo decide il server, o un client potrebbe inchiodare una coroutine e un socket per dieci minuti. Il tetto è `ATTESE_MASSIME` = 8, e superarlo **non è un errore** — si risponde subito, come se l'attesa non fosse stata chiesta, e il client ripiega da sé sul polling.
  **Misurato sul dispositivo** (Redmi Note 7, Android 10, 2026-08-23) con il telefono in **Doze forzato**, schermo spento e processo tenuto vivo dal solo `WebServerService`: la connessione appesa arriva intera alla scadenza, il risveglio su una scrittura ha mediana **70 ms** (10 prove, max 156), la scadenza **non slitta** (25,06 s in Doze contro 25,07 s da sveglio) e con **otto** attese appese il telefono resta in `mState=IDLE` con **zero wake lock** dell'app. Un handshake TLS costa 13–32 ms, quindi un'attesa scaduta ogni 25 s costa quanto il polling di prima ogni 30 s. **Il limite della prova va conosciuto**: telefono e computer erano su sottoreti diverse, quindi l'HTTP è passato da `adb forward`, cioè da USB — la radio Wi-Fi non è stata provata, e l'USB attaccato è la spiegazione più semplice del fatto che la scadenza non slitti.
  **Due cose dell'attesa sembrano dettagli e non lo sono.** (1) Il contatore delle versioni si legge **prima** di comporre il corpo: al contrario, una scrittura che cadesse in mezzo non sveglierebbe nessuno, e il difetto si manifesterebbe come «ogni tanto la pagina è in ritardo di venticinque secondi». (2) A ogni segnale il corpo si **ricompone e si ricontrolla**: su `events` si scrive anche per cose che i promemoria aperti non vedono — un evento già completato, un tombstone dalla sincronizzazione — e rispondere `200` su quei segnali manderebbe il browser a ridisegnare per niente, in un ciclo stretto. `READ_TIMEOUT_MILLIS` in `HttpServer` **non c'entra e non va alzato**: è un `soTimeout`, cioè un limite alla *lettura*, e quando si aspetta non si legge più niente.
  **Il segnale nasce dall'invalidazione di Room** (`invalidationTracker.createFlow("events")`, cablata in `ReminderApp` perché è l'unico punto che ha in mano il database e non solo il DAO), non da chiamate nei punti di scrittura. Quelli sono cinque — editor, completamento, snooze, `SyncEngine`, `ScrittureWeb` — e un sesto arriverà: un posto in più da cui scrivere sarebbe un posto in più in cui dimenticarsi di annunciare, e quel difetto non si vede, perché la pagina sembra solo lenta. Stesso argomento di `ScrittureWeb` per le sveglie. Il presidio è il test che scrive **dritto sul DAO** e pretende che l'attesa si svegli.
  **Il ridisegno è mirato: si tocca solo la scheda cambiata.** `riconcilia(precedenti, nuovi)` è una **funzione pura** che restituisce operazioni (`inserita`/`aggiornata`/`invariata`) e non tocca il DOM; l'applicazione cammina l'ordine di arrivo e usa `insertBefore`, che su un nodo già presente lo **sposta** invece di duplicarlo — così il riordino è una riga e non un caso a parte. Chiave: `id`, che è nel payload dalla 002. Una scheda che si sposta senza cambiare è `invariata`, perché il riordino nasce dal fatto che *un'altra* ha cambiato data. **`card._evento` si riscrive su ogni operazione, anche `invariata`**: i campi visibili possono essere identici mentre `updatedAt` è andato avanti, e lasciare lì i dati vecchi farebbe dichiarare al controllo ottimistico una versione che non esiste più.
  **I dati vivono sul nodo, non nella closure dei gestori.** Prima i pulsanti catturavano l'evento e funzionava perché una scheda viveva meno di un aggiornamento; da quando si riusano, la closure sopravviverebbe ai dati e un tocco su «Fatto» manderebbe l'`updatedAt` di quando la scheda è nata — cioè un `409` incomprensibile su una scheda che mostra il valore giusto.
  **Sulla scheda si scrive con `classList`, mai con `className`.** Assegnare `className` sovrascrive l'intera lista di classi, evidenziazione compresa, e il difetto sarebbe intermittente per costruzione: sparisce solo se il ricalcolo dei colori passa nei due secondi in cui l'evidenziazione è accesa. Vale in entrambe le direzioni.
  **La scheda cambiata si evidenzia, ma non alla prima risposta.** È il rovescio dell'aggiornamento mirato: togliere il ridisegno totale toglie il lampeggio e nello stesso gesto toglie il segnale. Alla prima risposta ogni scheda è «appena inserita» — evidenziarle tutte sarebbe far lampeggiare la pagina all'apertura, il difetto rientrato dalla porta di servizio — e per questo si guarda `primaRisposta`; stessa cosa alla chiusura del modulo, dove il confronto è contro dati vecchi di minuti. In CSS l'evidenziazione compare di scatto e svanisce piano, e le due velocità si ottengono con `transition: none` sulla classe accesa: quando viene tolta torna la transizione di `.evento`.
  **Il ciclo di rete si riprogramma da sé e ha un pavimento** (`INTERVALLO_MINIMO` = 5 s fra due richieste che non hanno portato niente). Senza, un telefono che risponde subito — una versione precedente che `attendi` non lo conosce, oppure il tetto delle attese superato — trasformerebbe «riparti appena arriva» in un ciclo stretto che martella la porta. Con il pavimento quei due casi degradano in un polling ogni cinque secondi. La scheda nascosta **interrompe la richiesta in corso** (`AbortController`), non solo il timer: senza, ogni scheda dimenticata terrebbe una coroutine e un socket per venticinque secondi e consumerebbe il tetto. E c'è una guardia sul `fetch` che non si risolve mai, perché quel guasto lascerebbe la pagina a mostrare dati vecchi **con l'aria di essere aggiornata**.
  **L'indirizzo si copia toccando la riga**, non solo l'icona: su un telefono è il bersaglio grande e ovvio, e ridigitarlo sull'altro dispositivo è la fatica che quella riga esiste per togliere. L'icona `ContentCopy` non è fra le 56 di `material-icons-core` (c'era solo `Share`, che promette un'altra cosa): è ridefinita in `ui/icons/`, come `Restore` e `Sync`. La conferma la dà l'app **solo sotto Android 13**: dalla 13 la mostra il sistema, e sovrapporvi la nostra direbbe due volte la stessa cosa — è la ragione di `sistemaConfermaLaCopia()` in `platform/`.
  **Le date le formatta il browser** (fuso del client), mentre `notificationMillis` lo calcola il server perché la formula non venga riscritta in JavaScript. La conseguenza voluta: la fascia cromatica si aggiorna al passare dell'ora **senza** una richiesta di rete. In scrittura vale lo stesso fuso, quindi sulla pagina quel che si imposta è quel che si legge; la divergenza con il telefono, se i due sono in fusi diversi, esisteva già in lettura e la scrittura non ne aggiunge.
  **Il modulo di modifica sta in un `<dialog>` fuori da `#elenco`, e il ridisegno si sospende mentre è aperto.** Restano due difese, ma dalla 005 non più per lo stesso difetto di prima: il ridisegno non azzera più l'elenco. Fuori da `#elenco` perché lì dentro il modulo sarebbe appeso a **una scheda**, che può sparire se il promemoria viene completato altrove; sospeso perché la riga in modifica è una scheda dell'elenco *sotto* il dialogo, e aggiornare le altre può spostarla — l'ordine dipende dalla data — lasciando a chi chiude un contesto cambiato sotto. Nessun errore chiude il modulo: il testo digitato resta dov'è.
  **`[hidden] { display: none !important }` non è cosmesi.** L'attributo nasconde solo perché la stylesheet del browser gli dà `display: none`, e qualunque regola d'autore lo scavalca: la barra dell'annullamento, che ha `display: flex`, compariva vuota su ogni pagina. La pagina si regge su `hidden` per quattro elementi.
  **La barra dell'annullamento è ancorata alla finestra, non al documento.** Nel flusso finiva sotto l'elenco, fuori schermo, mentre chi aveva appena toccato «Fatto» guardava il punto dove la riga era sparita: un annullamento che non si vede non è un annullamento.
  **Il `403` aveva due significati e li distingueva il client dal contesto; dalla 006 sono due codici** (`401` e `403`) e il client non deve più indovinare. Serve a una decisione precisa: su `401` il token conservato si **cancella** e il ciclo si **ferma** — senza, la pagina ripartirebbe ogni cinque secondi bruciando la soglia dei tentativi per niente — mentre su `403` non si cancella niente, perché quel token è buono. La bandiera che ferma il ciclo è **nuova e non `fermato`**: quella appartiene a `visibilitychange`, e riusarla vorrebbe dire far ripartire il ciclo a ogni riscoperta della scheda.
  **Il trasporto è TLS con un certificato autofirmato** (feature 003), e la conseguenza che governa tutto il resto è che **nessuno lo valida**: il browser avvisa una volta, l'utente scavalca. Da lì discendono tre cose che sembrano sviste e non lo sono. (1) Il certificato **non si riemette mai** — non al cambio di indirizzo, perché il `subjectAltName` non lo verifica nessuno; non alla scadenza, perché un certificato scaduto continua a funzionare lo stesso e riemetterlo sarebbe un avviso regalato. La guardia è in un punto solo, `CertificateStore.caricaOCrea`, e serve perché `apri()` è chiamato anche da `resume()`, cioè da `MainActivity.onStart()`: senza, l'avviso tornerebbe **a ogni rotazione dello schermo**, ed è un difetto che in prova non si nota perché chi verifica accetta l'avviso per riflesso. (2) Un difetto nel codificatore DER scritto a mano non apre un buco, cambia la forma di un avviso: per questo `Der.kt` è codice ordinario e non codice di sicurezza. (3) La chiave privata sul telefono può fingersi solo questo server — non è il caso di una CA, che è la ragione per cui la CA è stata scartata.
  **`KeyStore.getInstance("PKCS12")` va chiesto per nome**: su Android il predefinito è **BKS** (verificato su API 26, 29 e 33), e affidarsi a `getDefaultType()` romperebbe solo sul dispositivo, dove i test non arrivano. Stesso discorso per i protocolli: l'elenco predefinito comprende **TLSv1 e TLSv1.1**, quindi `apriSocket` abilita l'intersezione con {1.2, 1.3} invece di un elenco fisso — su API 26 il 1.3 non c'è e pretenderlo farebbe fallire l'apertura. L'`SSLContext` si costruisce **una volta sola**: ricostruirlo a ogni apertura costava ~50 ms sul thread principale a ogni `onStart`, e la sua cache di sessioni TLS è ciò che rende sopportabile l'assenza di keep-alive (pagina intera con sette handshake: 77–115 ms misurati).
  **Chiave e certificato stanno in due file DER** (`filesDir/web-tls/`), non in un PKCS#12: un archivio su file vuole una password, e una password scritta nel sorgente dichiarerebbe una protezione che non esiste. Protegge i permessi, come per il `sharedSecret` in `peers`.
  **L'impronta SHA-256 mostrata dall'app va confrontata a vista**, ed è l'unica cosa che distingue «cifrato» da «cifrato e autenticato»: scavalcando l'avviso si accetta *qualunque* certificato, quindi contro un attaccante attivo TLS da solo non basta. È lo stesso argomento del codice a sei cifre di `Pairing`.
  **Non è una PWA installabile sulla rete locale**, e dalla 006 l'ostacolo è rimasto uno solo: l'indirizzo fisso toglie la questione dello `start_url` con il token dentro, ma non quello che conta. Il service worker non c'entra (Chrome non lo pretende) e nemmeno lo schema: con `https://` l'origine sarebbe un secure context. È il **certificato non fidato** a fermare l'installazione. Verificato: su `127.0.0.1` — via `adb forward` — Chrome offre «Installa», perché il loopback è comunque un contesto sicuro; sullo **stesso servizio raggiunto a un indirizzo di rete**, con l'avviso scavalcato, il pulsante «Installa» **non compare**. Sbloccarlo richiederebbe un certificato fidato, cioè la CA locale scartata dalla feature 003.


**Desktop specifics:**
- Allarmi: una coroutine in attesa per evento; `DesktopAlarmScheduler.bootstrap()` riprogramma i futuri e notifica gli scaduti all'avvio.
- Notifiche: `notify-send` (libnotify ≥ 0.8) con azioni `-A`; l'azione scelta arriva su stdout.
- `kotlinx-coroutines-swing` è obbligatoria: senza `Dispatchers.Main` sulla JVM, `viewModelScope` non parte e la UI resta vuota senza errori.
- Database in `~/.local/share/promemoria/` (XDG), autostart in `~/.config/autostart/promemoria.desktop`.
- Integrazione col desktop (`DesktopIntegration`): voce in `~/.local/share/applications/` e icona in `hicolor`, così la barra delle applicazioni riconosce la finestra invece di darle un'icona generica. Il legame è `StartupWMClass`, che **deve** combaciare con il `WM_CLASS` della finestra — e quello **non si può scegliere**: i JDK recenti ignorano `awt.appClassName` e lo ricavano dalla classe `main` sostituendo i punti con trattini (`it-agoldoni-reminder-desktop-MainKt`). Per questo `wmClass()` lo calcola con la stessa regola invece di scriverlo a mano.
- Identità del dispositivo: file `device-id` accanto al database su desktop, `SharedPreferences` su Android (`localDeviceId()` in entrambi i `platform/`).

**Key conventions:**
- UI language is Italian throughout (labels, messages, date formatting).
- Debug builds use application ID suffix `.debug` and distinct app name.
- `advanceMinutes` on `EventEntity` controls how far before `dateTimeMillis` the alarm fires (alarm time = `dateTimeMillis - advanceMinutes * 60000`).
- Dependencies are managed via version catalog in `gradle/libs.versions.toml`.
- Java 17 source/target compatibility, Kotlin 2.3.21, KSP 2.3.11 (è KSP a fissare la versione di Kotlin), AGP 8.13.2, Compose Multiplatform 1.11.1.
- Le icone vengono da `material-icons-core`: `material-icons-extended` pesa 37 MB e le due icone mancanti (`Restore`, `Sync`) sono ridefinite in `ui/icons/`.
- Il piano di lavoro del port desktop è in `docs/features/001-desktop-linux/`; quelli della web app in `docs/features/002-web-app-android/`, `003-https-web-app/`, `004-scrittura-web-app/`, `005-aggiornamento-mirato-web-app/` e `006-indirizzo-fisso-web-app/`.
